## Provenance findings

### MakeHuman / MPFB

The existing project evidence records MPFB/MakeHuman core graphical assets under CC0 and separately records the add-on/program license. It also records that no third-party contributed MakeHuman assets were installed or referenced for the accepted character pipeline. The upstream license texts are retained under `third-party-notices/mpfb/`.

### Google Gemini-generated BGM

The six committed BGM tracks were generated by the project owner using Google Gemini. Google's current general terms state that Google does not claim ownership over original generated content from services that support generation, while users remain responsible for third-party rights and applicable law. These tracks are documented in `THIRD_PARTY_NOTICES.md` and are not included in the Apache-2.0 software grant.

## Repository hygiene policy

Keep production source, runtime assets, tests, and curated acceptance evidence. Do not commit transient deformation dumps, CI output, temporary screenshots, local Blender/MCP state, repeated WIP captures, generated project-tree snapshots, or ad-hoc patch dumps. Large editable source media follows `.gitattributes` Git LFS rules.

The public-readiness cleanup removed large tracked intermediate evidence from the current tree without rewriting historical commits.

## History and privacy decision

History rewriting is intentionally avoided by default because this project's existing PR/maintenance history is useful evidence of sustained open-source maintenance. A rewrite should occur only if a real secret is discovered or the owner decides that historical commit-email exposure is unacceptable.

Before the final visibility switch, the remaining mandatory decision is therefore:

1. run/confirm a full-history secret scanner with access to the Git repository; and
2. explicitly accept the historical author-email exposure or perform a dedicated email rewrite.

Changing future Git settings to a GitHub `noreply` address does not alter the email stored in old commits.

## Post-public protection sequence

GitHub Free supports branch rulesets/protected branches for public repositories. The committed recipe intentionally fits a solo-maintainer project:

- require every update to the default branch to go through a pull request;
- require review threads to be resolved;
- block branch deletion;
- block non-fast-forward / force-push updates;
- require **0 approvals** for now, because a sole maintainer cannot approve their own pull request;
- do not require CI status checks until the current GitHub Actions billing/spending-limit blocker is resolved.

`CODEOWNERS` remains useful for ownership/routing, but hard-requiring Code Owner approval should wait until at least one additional trusted maintainer can approve owner-authored pull requests.

After publication, import `.github/rulesets/main-protection.json` from **Settings → Rules → Rulesets → New ruleset → Import a ruleset**, review it, and create it as Active.

Then confirm **Settings → Actions → General → Workflow permissions** defaults to read-only repository contents, and enable **Settings → Security / Advanced Security → Private vulnerability reporting** when the public-repository option is available.

GitHub secret scanning is available for public repositories and scans the repository's Git history across branches. Review any resulting alerts immediately after the visibility switch; if a real credential is found, revoke/rotate it before treating the repository as safely published.

## GitHub integration limitation

The connected GitHub App can modify repository files and pull requests but currently receives HTTP 403 for the Secret Scanning Alerts, Branch Protection, and repository-level Actions-permission APIs while this repository is private. Those account/repository settings cannot be truthfully marked complete from this integration alone and must be verified through an authorized GitHub settings surface during the final visibility transition.
